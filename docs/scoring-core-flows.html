One task, end-to-end: agent runs in a browser, trace is captured, judge produces a verdict, binary score is written.

    "agent_steps": ["Step 1: ...", "Step 2: ..."],
    "ground_truth": "..." | null,
    "screenshots_b64": ["<base64 PNG>", "..."]
  },
  "metrics":   { "steps": 3, "duration": 16.05, "cost": 0.0 },
  "judgement": {
    "reasoning": "...",
    "verdict": true,
    "failure_reason": "",
    "impossible_task": false,

Binary scoring: there is no partial credit. impossible_task and reached_captcha are diagnostic flags only — they do not change the score.

F3Judge message construction

Exactly what the judge LLM sees, and how inputs are shaped before invocation (judge.py:28–198).

Rubric (system prompt) — priority order

  1. Ground truth (when present) — absolute precedence; verdict false if not satisfied.
  2. Task Satisfaction — did the user's goal happen?
  3. Output Quality — format / completeness match.
  4. Tool Effectiveness — % tools that succeeded.
  5. Agent Reasoning — planning, decisions.
  6. Browser Handling — crashes, page loads, captchas force a very low score.

Auto-fail conditions

  • Captcha / missing auth.
  • Wrong / missing output format.
  • Infinite loop or severe technical failure.
  • Browser crash or page never loaded.
  • Critical user requirement ignored.
  • Agent called done before completing all key points.
  • Agent fabricated content not in screenshot / DOM.

Response schema (Pydantic) — JudgementResult

class JudgementResult(BaseModel):
    reasoning: str | None
    verdict: bool                    # the score (1/0)
    failure_reason: str | None
    impossible_task: bool = False    # diagnostic only
    reached_captcha: bool = False    # diagnostic only

Conditional ground-truth block (injected into system prompt)

**GROUND TRUTH VALIDATION (HIGHEST PRIORITY):**
The <ground_truth> section contains verified correct information for this task.
This can be:
- Evaluation criteria (e.g. "Must extract exactly 5 items")
- Factual answers (e.g. "6", "Paris")
- Expected outcomes (e.g. "Google Doc must be created")
The ground truth takes ABSOLUTE precedence over all other evaluation
criteria. If the ground truth is not satisfied by the agent's execution
and final response, the verdict MUST be false.
All four text inputs are independently truncated to 40 000 chars; only the last 10 unique screenshots are sent.

F4Failure / timeout branch

What happens when an agent doesn't reach the judge — the judge never runs and the task scores 0 automatically.

Timeout return payload

{
  "task_id": "...",
  "score": 0,
  "steps": 0,
  "duration": 1800,
  "cost": 0,
  "error": "Task timed out after 1800s"
}
Per-task ceiling: TASK_TIMEOUT = 1800 seconds (30 min). No retries: a timed-out task is a permanent 0 for the run.

Exception return payload

{
  "task_id": "...",
  "score": 0,
  "steps": 0,
  "duration": 0,
  "cost": 0,
  "error": "<ErrorType>: <message>",
  "traceback": "..."
}
In both failure paths the per-task run_data/<task_id>.json trace file is not written, so the local viewer will not list a failed task — it appears only in the aggregate run row as a missing success.

F5Per-run aggregation

After all tasks for a run complete, one row is appended to the model's results history file.

Run row schema

FieldMeaning
run_startTimestamp YYYYMMDD_HHMMSS; identifies the run.
tasks_completedNumber of task results returned (incl. timeouts & exceptions).
tasks_successfulCount of score == 1.
total_stepsSum of agent step counts across all tasks.
total_durationSum of per-task wall-clock duration (seconds).
total_costSum of per-task LLM cost (USD).
Run-level accuracy = tasks_successful / tasks_completed (computed downstream by generate_plots.py, not stored here).

F6Leaderboard aggregation (multi-run)

How generate_plots.py turns the per-model history files in official_results/ into the published mean accuracy with a 95% bootstrap CI.

Decision matrix

ConditionEffect on leaderboard
tasks_completed < 100Run discarded with warning.
tasks_completed = 100, all score=0Run kept; contributes 0.0 accuracy.
Only 1 valid run for a modelBootstrap CI degenerates (mean = single value).
≥ 2 valid runsBootstrap 95% CI reflects judge / browser variance across runs.
total_duration = 0Tasks-per-hour row skipped to avoid div-by-zero.
Bootstrap CI is over runs, not tasks. With few runs the interval can be wide; it does not represent task-level statistical power.

Bootstrap CI (95%, percentile method)

def bootstrap_ci(values, n=1000):
    arr = np.array(values)
    means = [np.mean(np.random.choice(arr,
                                      size=len(arr),
                                      replace=True))
             for _ in range(n)]
    return (float(np.mean(arr)),
            float(np.percentile(means, 2.5)),
            float(np.percentile(means, 97.5)))
